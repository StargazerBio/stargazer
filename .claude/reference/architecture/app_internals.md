# App Tier — Internals (agent reference)

Deep, implementation-level detail for the `app/` deployment tier. This is the verbose companion to the human-facing [docs/architecture/app.md](../../../docs/architecture/app.md) — it carries the cross-cutting protocol detail (identity, the workspace store, pod lifecycle, hydrate and save) that spans several modules and so belongs to no single module docstring. When you change auth, storage, pod launch, or workspace sync, read this first and update it after.

Module-local behavior lives in each module's own docstring (`spec:`-linked back to the architecture doc); this file is only for the multi-module protocols.

## Identity (Union auth)

Both app kinds run `requires_auth=True`. Union's ingress gates every request on its login (an anonymous request gets a 302 to the tenant sign-in page) and forwards the signed-in user as headers it sets itself, **overwriting any client-sent value** (measured on the tenant):

| Header | Value | Used for |
|---|---|---|
| `X-User-Subject` | stable Union user id, bare (e.g. `387300641116005877`) | every per-user key |
| `X-User-Claim-Email`, `X-User-Claim-Name` | JSON-encoded strings (`"\"a@b.c\""`) | display only |
| `X-User-Token` | `IDToken <JWT>` from a browser, `Bearer <JWT>` from the CLI or an API key | on Union, the only proof of who's asking (below); stripped before marimo |

No GitHub login, id or token is forwarded. The browser's Union session cookies (`flyte_idt`, `flyte_at_*`, `flyte_user_info`) also reach the pod.

`app/identity.py` parses these: `user_from_request` returns a `User(subject, email, name)` or None. Everything per-user derives from the subject:

- the user's project: `u-<handle>`, created by onboarding (see Onboarding)
- workspace store prefix: `<root>/users/<subject>/`
- `_owner` on assets: the subject (an email would leak into public bylines)

**Union's gate needs view permission on the app's project.** A signed-in org member with no role on the project gets 403; with `viewer` they get in. Org membership alone isn't enough, and anyone with `viewer` sees every app in the project in the console. Gate decisions are cached per browser session for several minutes. This is why every user has their own project.

**Bearer tokens work too.** A request with `Authorization: Bearer <access token>` passes the gate as that user, which is how a second identity can be exercised from the CLI.

**The in-cluster address skips all of it.** Every app also answers at `http://<app>.<project>-<domain>.svc.cluster.local`, with no login and no header rewriting. Forged `X-User-Subject`, `X-User-Claim-Email` and `X-User-Token` sent from a task in another project to a user's apps arrive unchanged at an echo app; the dashboard served its home page and the owner's private asset list (200); a notebook pod served marimo's editor page (200), whose kernel runs with `--no-token`. So on Union identity is the token alone. It's an RS256 JWT from `https://signin.us-west-2.unionai.cloud` (`config.AUTH_ISSUER`, set for the `union` target), checked against the keys its discovery document names (`/oauth/v2/keys`), with its expiry checked (60 s leeway) and its audience not: the subject is its `sub`, which equals `X-User-Subject` through the gate (measured with a CLI token: `iss` as above, `kid` among the published keys). `X-User-Subject` itself is ignored there; the claim headers are still read, for display only.

## Onboarding

Onboarding (the `stargazer-users` CLI, its flags and its checks) lives in the `StargazerBio/infra` repo, which also holds every AWS operation. An org admin runs it with their own CLI identity, since app and task pods can't create projects. This repo owns the contract it deploys through, `app/deploy.py`:

- **Naming.** A user's project is `u-<handle>`. `login_for` maps it to the DSQL login and table name, `iam_role_name` to the index's IAM role, and `dsql_index_url` builds the `dsql://` URL from the cluster ARN and those names alone (The Asset Index below).
- **Dashboard.** `deploy_dashboard(project, owner_subject, extra_env)` serves `app_env` itself, its `env_vars` and `domain` set for this user (not a `clone_with` copy, which breaks `include=`; see the comment in the function), into the project at `Domain(subdomain=<project>)`. The env carries `FLYTE_PROJECT`, `SG_OWNER_SUBJECT`, `STARGAZER_OWNER`, `STARGAZER_NOTEBOOK_IMAGE`, `STARGAZER_INDEX_URL`, `STARGAZER_VERSION`, and, when set, `STARGAZER_STORE_ROOT`, `STARGAZER_ADMIN_SUBJECTS`, `STARGAZER_PUBLIC_ASSETS=off` and `FLYTE_ORG` (Deploy Settings below). The subdomain is unique because project ids are: Union does **not** reject a second app asking for a taken subdomain, it leaves it stuck at "App created" with no endpoint. A serve-watch failure on a redeploy is checked against the app's real state before it's reported.
- **Project key.** Union injects no key into pods (`unionAuth.injectSecret: false` in the cluster config), and a pod without one has no identity: flyte's in-cluster client falls back to a browser sign-in, so a parent task's child launch fails (`address already in use` on its localhost callback) and a dashboard's in-pod image build hangs. So on the `union` target `STARGAZER_SECRETS` adds `flyte.Secret(key=PROJECT_KEY_SECRET, as_env_var="_UNION_EAGER_API_KEY")`, the variable `init_in_cluster` reads first, and every task environment, `app_env` and per-notebook env declares it. Infra's onboarding creates the key with only the user's project policy and stores it as secret `UNION_API_KEY` in the project's `FLYTE_DOMAIN`; `PROJECT_KEY_SECRET` is the name both repos use. The devbox declares none: its webhook refuses a pod whose declared secret is missing, and it has no login to call.
- **Release.** Redeploying every user's dashboard is the release step. Images are content-hashed, so each builds once per run; the bundle is taken from the deployer's working tree at each deploy, so the checkout shouldn't change during one.

## Access

Union only proves the visitor can view the project, and that check never runs on the in-cluster address. So on Union both app kinds check for themselves: the token's subject must be the owner (`SG_OWNER_SUBJECT`, baked in by `deploy_dashboard`) or one of the org admins the deployer names (`STARGAZER_ADMIN_SUBJECTS`, `config.ADMIN_SUBJECTS`). Off the `union` target there's no issuer, the headers are taken as they come, and whoever arrives gets in.

- **Dashboard.** Routes take `CurrentUser` (`identity.current_user`): 401 without a valid token, 403 for a signed-in stranger, otherwise the visitor's name/email with `subject` replaced by `config.OWNER_SUBJECT`, so storage and pod ownership follow the dashboard's owner. With no owner configured (local run) the visitor's subject is the key. The asset routes read the same verified identity (`user_from_request`). The dashboard serves no index routes; the database checks who reaches the index (The Asset Index below).
- **Notebook pods.** The proxy's `_TokenGate` (`app/proxy.py`) runs the same check on every HTTP and websocket request, the terminal and marimo's kernel socket included: 401 or 403, and a websocket is closed with 1008 before it's accepted. `/launch` gives the pod `SG_AUTH_ISSUER` and `SG_ADMIN_SUBJECTS`; `SG_OWNER_SUBJECT` also keys the hydrate/sync prefix. Before forwarding to marimo it strips `Host`, `Cookie` and every `X-User-*` header (`_forwardable`), so notebook code never sees a visitor's Union token through a request.

**Residual risk.** Code in a pod can still read anything in the pod, and the cookies do reach the pod's proxy process. A malicious owner could serve code that captures a visiting member's token before the strip. This risk is accepted.

## The Workspace Store

`app/workspace_store.py` owns the layout; no route composes a URI by hand.

```
<STARGAZER_WORKSPACE_ROOT>/users/<subject>/workspace/<path>
<STARGAZER_WORKSPACE_ROOT>/users/<subject>/settings.json
```

One object per file in the user's workspace, at its path. The user's dashboard settings are one JSON object beside it (`get_settings` / `put_settings`, `DEFAULT_SETTINGS` filling any key never saved: `save_interval_seconds` and `explorer_default`), outside the prefix a pod hydrates. The dashboard touches only the notebooks, the top-level `.py` files (a `.py` in a folder never lists as one), so it can list them and read one header without fetching the rest; the pod's proxy saves everything else. Subjects must match `[A-Za-z0-9_-]+` and filenames one plain `.py` segment, so a key can't escape its prefix. Create refuses to overwrite (`NotebookExistsError` → the 409 that create and copy rely on); get of a missing notebook returns None; delete is idempotent. Reads and writes go through `flyte.storage`, listing and deletes through the fsspec filesystem it resolves for the root, so the same code runs against `s3://` on the tenant and a local path in tests.

On Union the root is a prefix in the tenant bucket (`s3://union-us-west-2-stargazerbio/stargazer`). Every project runs as one IAM role (`union-us-west-2-stargazerbio-userflyterole`), so cross-project access works and, equally, any pod can read every user's objects. A local machine has no credentials for the bucket; only pods can reach it.

Without a root (a local run), store-backed routes return 503 and the Workspace section says saving isn't available.

## The Asset Index

Each user's index is `DsqlIndex` (`stargazer.utils.index`) on their own table in the org's Aurora DSQL cluster (`STARGAZER_DSQL_CLUSTER_ARN`; the cluster is in infra's OpenTofu, `aws/`). Pieces:

- **Names** — from `app.deploy`, which infra's onboarding imports too: project `u-jane` gets login and table `u_jane` (`login_for`; `-` can't sit in an unquoted identifier) in schema `assets` (`DSQL_SCHEMA`), and IAM role `stargazer-index-u-jane` (`iam_role_name`). `dsql_index_url` builds `dsql://u_jane@<id>.dsql.<region>.on.aws/assets.u_jane?role_arn=arn:aws:iam::<account>:role/stargazer-index-u-jane` from the cluster ARN alone, so a deploy needs no AWS access.
- **Isolation** — the EKS cluster uses IRSA. Every pod in `<project>-<domain>` runs as that namespace's `default` service account, with a projected token for audience `sts.amazonaws.com` (`AWS_WEB_IDENTITY_TOKEN_FILE`), and keeps the shared `userflyterole` as its default credentials, which has no DSQL permission. The user's role trusts only `system:serviceaccount:<project>-<domain>:default` and allows only `dsql:DbConnect` on the cluster. The login is mapped to it (`AWS IAM GRANT`), holds `USAGE` on `assets` and `SELECT`, `INSERT`, `UPDATE`, `DELETE` on its own table, and owns nothing: the admin owns the table, so the login can't alter or drop it, or create one. Measured on the tenant: a pod in `flytesnacks` is refused at `AssumeRoleWithWebIdentity`; the shared role can't log in as a user's login; a user's role can't log in as the admin; the login gets `42501` on another user's table and on `CREATE TABLE`.
- **Client** — `DsqlIndex` assumes the role with the pod's token, caches the credentials (renewed 5 minutes before they expire) and a signed token (10 minutes) per process, and connects afresh for every call, so DSQL ending a connection after an hour never reaches a caller. It connects over IPv4 only (pods have no IPv6 route and the endpoint resolves to both, so libpq would try the AAAA first), with `verify-full` against certifi's bundle and `sslnegotiation=direct` on libpq 17, and never runs DDL. `PostgresIndex._write` reruns a write refused with SQLSTATE 40001 (DSQL's answer to every write conflict) up to 10 times with jittered backoff, then raises. A process's first call takes ~720 ms (assume, sign, connect), later ones 21–41 ms.
- **Who reaches it** — the dashboard's asset explorer (`app.assets._get_index`, `stargazer.utils.index.make_index(STARGAZER_INDEX_URL)`), every notebook pod (`/launch` passes on the dashboard's own `STARGAZER_INDEX_URL`), and the runs those start (`stargazer.config._stargazer_env_vars()` forwards it, as it forwards any storage setting set explicitly). No index call goes through the dashboard, so redeploys and scale-to-zero never touch the index.
- **Plumbing** — `/launch` gives each notebook pod `STARGAZER_INDEX_URL`, `STARGAZER_STORE_ROOT` (the workspace root) and `STARGAZER_OWNER`, and declares the `PINATA_JWT` secret, as the dashboard does (`app_env`), so a notebook's queries take in the public tier and it can publish. The dropdown terminal doesn't get it: `_shell_env` in `app/proxy.py` still scrubs it, so an agent's `env` there doesn't put it in the agent's context. That's tidiness, not a boundary: any notebook can also get the key through a task that declares the secret. `deploy_dashboard` bakes `STARGAZER_STORE_ROOT`, `STARGAZER_OWNER` and the user's index URL into the dashboard.
- **Devbox** — `devbox/dashboard.py` passes the devbox's Postgres URL in `extra_env`, which `deploy_dashboard` takes in place of the DSQL URL. With neither a cluster nor an index of its own, a deploy is refused: the dashboard would fall back to a file on its own disk, which its pods can't reach and scale-to-zero erases.

## Pod Hydrate & Save

The pod is a working copy; the store is the durable one. The dashboard never calls a pod (a `requires_auth=True` pod is unreachable server-to-server), so the pod does both ends itself.

1. **Hydrate.** `launch-notebook.sh` runs `sg_proxy.hydrate()` before starting marimo: every object under the owner's `workspace/` prefix lands at its path in `/workspace` (`fs.find`, then each object's path relative to the prefix with the URI scheme stripped, since S3 lists `bucket/key`). A brand-new user, or a store failure, starts with an empty dir (logged, never fatal).
2. **Starting page.** The proxy answers immediately; until marimo is up, a browser request gets a self-refreshing "Starting your notebook…" page. `/__sg__/ready` reports 200/503 for scripts.
3. **Save on an interval.** A background loop walks `/workspace` (`_workspace_files`: no dotfiles or dot-dirs, no `__pycache__/` or `__marimo__/`, symlinks not followed) and uploads each file whose size or mtime differs from what it last stored, each to its own key. An unchanged file is never read. The stamps of just-hydrated files are seeded at startup, so the first pass doesn't re-upload them. A failed upload is logged and retried next pass. One PUT per object, so an interrupted upload can't leave a half-written file. The interval is `SG_SAVE_INTERVAL_SECONDS` on the pod, 30 when unset. `/launch` sets it from the user's `save_interval_seconds` setting (the header's Settings modal → `POST /settings`, a whole number of seconds, 0 or more), read at launch, so a running pod keeps the interval it started with. 0 starts no loop.
4. **Deletes follow.** A pass deletes from the store each file it hydrated or saved (a key of `_synced`) that's gone from `/workspace`. Nothing else: after a failed hydrate the workspace is empty, and mirroring it would wipe the store.
5. **Big files stay out.** A file over `MAX_SAVED_BYTES` (100 MB) is skipped without being read. `GET /__sg__/save-status` lists such files, read from disk on each request so it works with the loop off, and `app/save_banner.html`, spliced into every marimo page beside the terminal overlay, polls it every 10 s and shows each one with the cell that stores it as an asset (`default_client.upload(build_asset(...), Path(...))`), which writes from the pod straight to the store and the index.
6. **Save at shutdown.** The FastAPI `lifespan` shutdown hook cancels the loop and runs a final pass when Knative scales the pod to zero.

On the tenant, a cell added in a fresh edit pod is readable through the dashboard's Download route seconds later, and survives the pod scaling to zero and being reopened.

The signal path is load-bearing for step 6. Flyte's `fserve` wrapper is PID 1 and, on the Knative SIGTERM, forwards the signal to its **one direct child only** (`Popen(cmd, shell=True)` + `send_signal`). So uvicorn must be that direct child: the AppEnvironment args prepend `exec` (so the `sh -c` wrapper replaces itself with the launch script rather than lingering; Debian's `/bin/sh` does not reliably exec-collapse a bare `sh -c "script"`), and the launch script then `exec`s uvicorn into that slot. An intermediate shell anywhere in the chain swallows SIGTERM and the final save is silently skipped.

Receiving SIGTERM is necessary but not sufficient: uvicorn drains open connections and in-flight background tasks **before** running the `lifespan` shutdown. The proxy holds a long-lived task to the local marimo backend that never drains on its own, so with uvicorn's default `timeout_graceful_shutdown=None` the drain blocks forever and the final save never fires (verified empirically). The launch script therefore passes `--timeout-graceful-shutdown 15`, which bounds the drain, cancels the lingering task, and then still runs `lifespan.shutdown`. 15s sits well under the pod's 300s termination grace period.

## Creating Notebooks & Per-Notebook Resources

The Workspace section offers a **New notebook** create tile (name + blank|basic seed only — resources and the tile blurb are set afterward). The seeds are real notebook files in the package — `notebooks/templates/blank.py` and `basic.py` — not generated source. `POST /workspace/create` slugifies the name, copies the chosen seed, declares the typed name as `main_name` in its setup block (`with_setup_values`; the seed's own `main_env` stays), writes it to the user's store (`create_workspace_notebook`, no-overwrite → 409), and **returns the rendered tile HTML**. The seeds are read from the installed package, not a checkout. (Notebooks don't pin marimo in their PEP 723 headers — `marimo --sandbox` injects the image launcher's version into each kernel venv, so the two never skew without per-notebook bookkeeping.) Create is a pure "add a notebook" action: the browser drops that tile into the Workspace grid; it does not launch or navigate. Both seed slugs are reserved create names and filtered out of the dashboard's tile listing. A new name (Create, Copy, Open from GitHub) can't take a built-in notebook's slug either, since a workspace notebook's app is named `nb-<slug>-<mode>` like a built-in one's; Create refuses either kind as taken by a built-in notebook, and Open from GitHub answers 409 saying so. A notebook already stored under a built-in slug stays manageable.

Create refuses a name whose slug is over `NOTEBOOK_SLUG_MAX` (22) with a 400. Flyte won't deploy an app whose name is over 30 characters, and a notebook's app is `nb-<slug>-edit`. The cap is the same in every project: Knative names the service after the app alone, inside a `<project>-<domain>` namespace (a 31-character name is refused at deploy with `app.metadata.id.name: must be at most 30 characters`; a 30-character one deploys). When `serve` raises at launch and `App.get` then can't find the app, the deploy was refused, so `/launch` returns the serve error as a 422. Not a 502, whose body Cloudflare replaces (Errors, under Dashboard Routes), nor a 503 "still starting", which would invite retries that can't succeed. A watch error on an app that does exist still hands back its endpoint.

Each Workspace tile carries two corner controls:

- **Gear** → a code editor on the body of the notebook's setup block: everything under `with app.setup:` (a closing comment included), dedented flush left (`setup_body`). Opening it fetches the body fresh (`GET /workspace/setup`), since an open notebook saves its edits back; a notebook without a setup block gets a starter body. Save (`POST /workspace/setup`) is a 409 while the notebook has an active app in either mode (`_notebook_running`, an `App.get` per mode; one that can't be fetched counts as stopped), since the pod saves its own copy of the file whenever a cell changes and never rereads the store. Otherwise it normalizes CRLF and parses the body on its own, so a syntax error carries the editor's line number; `replace_setup_body` then indents it back under the block's own `with` line (keeping options like `hide_code=True`, or a plain `with app.setup:` after `app = marimo.App(...)` when there was none), checks that `main_name` and `main_description` read and that a declared `main_env` evaluates (`evaluate_main_env`, the launch's own check, inside `forget_new_environments`), a 400 with the reason otherwise and nothing written, splices it over the old block's lines, and returns the tile's new title and blurb, which the browser swaps in. Environment changes take effect at the **next** launch.
- **Trash** (`POST /workspace/delete`, workspace-only) removes `<slug>.py` from the store (idempotent — a file already gone still succeeds) and tears down any edit/run pod for that slug (deactivate, then delete the record), so deleting can't orphan a pod with no tile left to Stop it. The tenant bucket has versioning on, so a deleted notebook can be recovered from its version history.
- **Download** (`GET /workspace/download`) returns the notebook's `.py` as an attachment — the path for sharing a notebook upstream.

Seed slugs are rejected by both. The browser confirms delete, then drops the tile on success.

Resources are honored **as-authored — no ceiling**. At `/launch`, the dashboard reads a workspace notebook's source from the store and evaluates its `main_env` (below), which `per_notebook_env(declared=…)` takes. Tile names and descriptions are read with `ast` at every dashboard render (`app.notebook_meta`; no notebook code runs). `per_notebook_env` fills each resource field a declaration leaves unset from `stargazer.notebooks.NOTEBOOK_RESOURCES`, which is also `notebook_env`'s: one CPU, a `("2Gi", "6Gi")` memory request/limit (the scRNA workflow's, which declares none) and `NOTEBOOK_DISK` (20Gi) of ephemeral storage, which Union applies as request and limit both. Tutorials and workflows aren't read, so they get all of the defaults. Without it the pod's only ephemeral-storage limit is the Knative queue-proxy sidecar's 1Gi, and the kubelet evicts a pod whose sandbox venv, uv cache and workspace outgrow that, as a notebook with numpy and matplotlib does while its venv installs.

## Notebook-Declared Environments (`main_env`)

A workspace notebook can declare its pod's environment in its setup block, `main_env = notebook_env.clone_with(name=…, image=notebook_base.with_…(…), resources=flyte.Resources(…))`. The dashboard finds and evaluates it (`app/notebook_environment.py`) and layers its own fields on top (`per_notebook_env`); building is the SDK's.

- **Find.** `extract_main_env` reads the setup block's assignments (`app.notebook_meta.setup_assignments`, shared with the name and description), parsing the source with `ast` and looking only inside the top-level `with app.setup:` (or `app.setup(...)`) block, which is where marimo writes the setup cell; cells are functions and are never searched. The last assignment wins. Unparseable source declares nothing.
- **Evaluate.** `evaluate_main_env` `eval`s the expression in the dashboard process with only `flyte`, `notebook_base` and `notebook_env` in scope (the dashboard lacks each notebook's PEP 723 deps, so the rest of the setup block can't run), where `notebook_base` is `notebook_image_base(config.NOTEBOOK_IMAGE)` and `notebook_env` is `notebook_environment(notebook_base)`, the dashboard's own copies of what `stargazer.notebooks` gives the kernel. It raises `MainEnvError` (a 422 at launch, a 400 at the gear's save) when the expression raises, the result isn't a `flyte.app.AppEnvironment`, or its image isn't a `flyte.Image` whose `base_image` is the deployed notebook image (the pod needs the proxy, launch script and tools), and for an image with layers of its own off Union (`STARGAZER_TARGET` ≠ `union`), where there's no builder: the SDK would "assume the image exists" and deploy a bare `name:tag` no node can pull. An environment on the bare `notebook_base` needs no build, so it serves on the devbox too.
- **Layer.** `per_notebook_env(declared=…)` returns `declared.clone_with(…)` (`notebook_environment(base)` when there's no declaration) with the dashboard's fields: name `nb-<slug>-<mode>`, description, the launch args, port 8080, `requires_auth=True`, scaling, domain and `STARGAZER_SECRETS`, the declared env vars under the dashboard's (owner, issuer, admins, store and index), and resources filled per field. A field the dashboard doesn't set (pod template, service account, interruptible, timeouts, …) passes through from the declaration. An image equal to the bare base is swapped for `Image.from_base(config.NOTEBOOK_IMAGE)`, which `serve` treats as prebuilt. The clone is built in `app/per_notebook.py`, so its `_caller_frame` and `_declaring_file` point there.
- **Registry.** Every Flyte `Environment` appends itself to `flyte._environment._ENVIRONMENT_REGISTRY` in `__post_init__`, and only the CLI (`flyte deploy`, `flyte build`) reads it, not `serve`. `forget_new_environments` wraps the launch and the gear's check and drops, by identity, whatever registered inside, so a long-lived dashboard's registry stays its import-time size.
- **Build and serve.** The launch builds a declared image with `flyte.build.aio(image, wait=False)` (`ImageBuildEngine`: an existence check, one `GetImage` call, then a `system/build-image` run on the remote builder in the dashboard's project, which is the user's), and `serve.aio` deploys with the builder's fully qualified URI (`…/union/stargazerbio:notebook-custom-<hash>`). `init_in_cluster` already defaults to the remote builder. The tag hashes the base image plus the layers, so an unchanged declaration is an existence hit, and the lookup is org-wide: an image built from one user's project is found from any other (an image built from one project is found from another). A declaration builds once per release (each release's notebook image is a new base) for the whole org, however many notebooks or users share it. A built image (no build run comes back) is served at once. An unbuilt one answers `/launch` with 202 and the build run's URL, so no request waits out the platform's 300 s app request timeout: a background task (`_serve_when_built`, held in `_builds` by slug and mode so it isn't garbage-collected) waits for the run, then serves. A second launch during the build answers the same 202. A failed build is kept in `_builds` and reported by `/launch/status` until the notebook is launched again; the tile alerts it as it would a 422. A dashboard restart mid-build loses the task, but the build finishes, so the next launch serves at once. `ImageBuildEngine.image_exists` and `ImageBuildEngine.build` are `async_lru`-cached per process, a "not built" answer and the unwaited build's run included, so once the run ends the task drops that image's entries (`_forget_build`, reaching into `flyte._internal`); otherwise its serve, and every later launch, would submit another build. `ImageBuildError` (a build check refused, or a build that fails inside `serve`) is caught before the serve-watch recovery, which would otherwise hand back the app as last served, on its old image.
- **SDK fact it leans on.** `Image.from_base(uri)` refuses layers until it's `.clone(name=…, extendable=True)`, so `stargazer.notebooks.notebook_base` is that clone, named `notebook-custom`.
- **Pod env.** The pod's `STARGAZER_NOTEBOOK_IMAGE` is always the deployed image, never the declared one, since the kernel's `notebook_base` builds on it. Outside a hosted pod `notebook_base` stands on a `notebook-app:local` placeholder.

On the tenant, a first build of `notebook-app` plus one apt package takes about a minute (65.7 s from a task pod), and an identical second call is an existence hit in 0.5 s. A notebook declaring `jq` launches in about a minute end to end (the build run in the user's project, then the deploy) without hitting a request timeout, and a stop and relaunch from the tile starts no build. The basic workspace template declares a `main_env` whose image adds bcftools, so a notebook created from it exercises the same path.

## Running State (stateful tiles)

Tile run-state is unified and authoritative. The dashboard's launch/stop handlers are **event-delegated**, so dynamically added tiles (a freshly created notebook) work with no re-binding. On load the page calls **`GET /launch/status`**, which discovers deployments with **one control-plane list** (`list_project_apps` on the dashboard's own project, the same call cleanup uses), filters to `nb-{slug}-{mode}` names (`_parse_nb_name`; the mode is the last dash segment since slugs may contain dashes), then re-fetches each discovered name with `App.get` in parallel for authoritative status (list payloads may not carry full conditions). The active ones are returned with their plain endpoints; the page flips those tiles straight to **Open + Stop** instead of a fresh Edit/Run. Because it reads the control plane rather than in-memory state, it's correct across dashboard restarts, and because discovery is name-based it never probes notebooks that were never launched. A listing failure degrades to "nothing running" rather than an error. It also reports, from the dashboard's memory, launches whose image is still building (with the build run's URL) and builds that failed (with the reason); a building notebook isn't reported running even while an older pod of it is up. A building tile links to its build run in place of Edit/Run and polls `/launch/status` every 5 s until the notebook is running (Open + Stop) or its build failed (Edit/Run back, and an alert). Org-scoped calls like this list need the org, which in-cluster init can't discover in an app pod, so onboarding bakes `FLYTE_ORG` into the dashboard and the dashboard passes it on to notebook pods.

**Hydrated Open re-serves; fresh Open links directly.** A **fresh** launch (Edit/Run click → `/launch`) links straight to the returned URL. A **hydrated** Open (from `/launch/status` on load) instead **re-serves through `/launch` on click** before navigating, because a hydrated pod may have been served before a redeploy with an older image or env. Re-serving reconciles it to the current spec (a no-op for a warm, current pod). The tab is opened synchronously in the click handler and navigated once `/launch` returns, so the await can't cost the user gesture and trip the popup blocker. A scaled-to-zero pod needs no special handling: the platform wakes it on the first request and the proxy shows its starting page.

**One modality at a time.** A notebook runs in either `edit` *or* `run` mode, never both — there's no use case for two live pods of the same notebook, and forbidding it caps pod count at one per notebook. When a notebook is launched (or hydrated as already-running), the dashboard hides **both** the launched mode's own Edit/Run button *and* the other mode's, leaving only that pod's controls: **Open: Edit Mode** / **Open: Run Mode** and **Stop**. **Stop** restores both buttons. This is a client-side affordance: it removes the second-pod path from the UI rather than enforcing mutual exclusion in the control plane. There's no Save button: pods save themselves (see Pod Hydrate & Save).

A global **Clean up stopped apps** control, the broom in the dashboard header (`POST /workspace/cleanup`), deletes (`App.delete`) the deployment records for every *deactivated* `nb-{slug}-{mode}` app in the user's project — Stop deactivates an app but leaves the record; this removes them. Active/idle apps are left alone.

## Copy to workspace

**Copy makes a read-only source editable.** A workflow's or a public notebook's explorer card carries a **Copy to workspace** button → `POST /workspace/copy` (`slug` + `section`). The route resolves the source (`_copy_source`): a built-in workflow is read from the installed package (`builtin_source`), a public notebook from the gateway. It then writes it to the workspace via `create_workspace_notebook` and returns the rendered Workspace tile the browser drops before the New-notebook tile. The copy keeps the source's setup block, and the workflow's registry title and blurb are declared in it as `main_name`/`main_description` (`with_setup_values`, which adds a setup block to a notebook without one), so it tiles and launches like any user notebook. The target slug is derived from the source title (`_notebook_slug`); the store's no-overwrite create makes a name collision a **409**, so copy never clobbers an existing notebook. Copy is a pure "add a notebook" action: no launch, no navigation.

**Open from GitHub is copy from a link.** The Workspace grid's **Open from GitHub** tile posts a link → `POST /workspace/github` (`link`). `app/github_import.py` turns a `github.com/<owner>/<repo>/blob/<ref>/<path>.py` or `raw.githubusercontent.com/<owner>/<repo>/<ref>/<path>.py` link into its raw URL (anything else is a 400 before any fetch, so the dashboard can't be pointed at another host) and streams it from `raw.githubusercontent.com` without following redirects, stopping past `MAX_BYTES` (1 MB, a 413). GitHub's 404 is a 404 that says to check the link and that the repository is public; a body that isn't UTF-8, or a file `with_setup_values` can't place a setup block in (no `app = marimo.App(...)`), is a 400 saying it isn't a marimo notebook. From there it's copy: the title is the file's `main_name`, else its file stem, declared back with its `main_description`; a slug over `NOTEBOOK_SLUG_MAX` is refused like create; a collision, or a built-in notebook's slug, is a 409. The fetch's `httpx` transport is the module's `TRANSPORT`, which the unit tests replace with an `httpx.MockTransport`.

## The Proxy Data Path

- **Proxy:** the standalone `app/proxy.py` (which can't import the app package) keeps one module-local shared client with keep-alive to loopback marimo (`_upstream_client`, closed in the proxy lifespan after the shutdown save). Only `text/html` responses are buffered — for the terminal overlay and save banner splice; everything else (static bundles, API JSON, downloads) **streams** through chunk-by-chunk (`StreamingResponse` over `aiter_raw`, `BackgroundTask(resp.aclose)`) with its original headers, so large bodies never sit in proxy memory. The raw query string passes through untouched (duplicate params intact), hop-by-hop, cookie and `X-User-*` headers are stripped, and the request body is streamed only when one exists (no gratuitous chunked framing on GETs).
- **Concurrency:** the dashboard route reads each workspace notebook's header in parallel (best-effort).
- **Compression:** the dashboard runs `GZipMiddleware` (min 1KB) for the dashboard HTML and asset listings. The proxy does **not** — it relays marimo's own encoding untouched.

Private: opens a writer at `StorageClient.staging_uri` (`users/<owner>/uploads/<id>/<name>`). Public (503 without public assets): stamps the user's subject as `_owner` and creates Pinata's TUS upload (`PinataClient.tus_create`), whose checks make more than `MAX_KEYVALUES` (9) stamped keys, or a key or value over `MAX_KEYVALUE_CHARS` (250), a 422 before anything reaches Pinata. → 201 with `Location: /assets/tus/<id>` |
| `HEAD /assets/tus/{id}` | signed in, and the user who started it (either network) | `Upload-Offset` and `Upload-Length` for a client resuming; 404 for an unknown or expired upload, 403 for an upload someone else started |
| `PATCH /assets/tus/{id}` | signed in, and the user who started it (either network) | Appends the body at `Upload-Offset` (409 with the current offset when it differs; 415 without `application/offset+octet-stream`). Private: each piece is written, fed to the `CidBuilder` and counted as it arrives, so a dropped request resumes from what landed. The completing piece closes the writer, works out the CID and calls `StorageClient.adopt` (a row pointing at the upload, `_owner` stamped; or, when the CID is already stored, the upload deleted and the existing row kept). Public (`_patch_public`): the body is held whole, at most `TUS_CHUNK_BYTES` (else 413), sent as one `PATCH` to Pinata's upload (`PinataClient.tus_patch`), then fed to the `CidBuilder` and counted, so the offset never runs ahead of Pinata's. On the completing piece, Pinata's `Upload-Cid` must equal the builder's; otherwise the Pinata file is deleted and the response is a 422, which tus-js-client doesn't retry (a 5xx would be retried into a 404 and a fresh upload of the whole file). → 204 with `Stargazer-Cid` |
| `POST /assets/update` | public: signed in + record **owner** / private: **owner** | Public: fail-closed ownership (record's `_owner` must equal the user's subject, read fresh) → `build_asset()` validate patch → the route puts the user's subject in the patch as `_owner` → `PinataClient.update_metadata()` merge → updated record. A key or value over `MAX_KEYVALUE_CHARS` (250) is a 400, raised before the PUT, which would otherwise answer 256+ with a bare "malformed" 400. Private: `build_asset()` validate → `index.merge` with `_owner` restamped (404 for an unknown CID) |
| `GET /assets/download/{cid}?network=` | public, stargazer: none / private: **owner** | Public: 302 redirect to `PINATA_GATEWAY`. Private: the row's `uri` streamed back through the dashboard as an attachment (`flyte.storage.get_stream`), not a presigned redirect: one path for a local store and the bucket. Stargazer: the built-in notebook whose file has that CID (`notebooks.builtin_path`), as an attachment; 404 for any other CID |

**TUS uploads** live in the dashboard's memory (`_tus_uploads`): the uploader's subject, the writer (private) or Pinata's upload URL (public), the offset, the CID builder, a per-upload lock. The writer is `flyte.storage.open(uri, "wb")`, obstore's multipart writer (10 MiB parts), on an object store, and a threaded local file (`_LocalWriter`) when the store root is a plain path. Every TUS request first drops uploads idle past `TUS_IDLE_SECONDS` (1 h). A dropped upload's writer is let go without `close`, which would complete a partial object, so its parts stay in the bucket unfinished; the pods' role can't abort a multipart upload, so clearing them is the bucket's job (an `AbortIncompleteMultipartUpload` lifecycle rule). An idle public upload is just forgotten; Pinata's side expires on its own. The browser (`tus-js-client` 4.3.1 from jsDelivr) sends `TUS_CHUNK_BYTES` (48 MiB, rendered into the page) pieces, under Cloudflare's per-request body limit and Pinata's 50 MB per-`PATCH` limit, keys each remembered upload by its network as well as the file (both networks share the endpoint), retries while online, waits for the `online` event when offline, and resumes after a reload from the upload it remembers for the file.

**Owner** on the private routes is the dashboard's: the signed-in subject must equal `SG_OWNER_SUBJECT` (403 otherwise, 401 anonymous). Locally, with no owner baked in, any signed-in user passes. On the upload, update and download routes, which act on one record's store, the `network` is `private` (the listing's `mine`) or `public`, plus `stargazer` for a download; anything else is a 400.

## Asset Manager (mechanics)

**The key is a secret; private assets never touch Pinata.** `app_env` declares `secrets=STARGAZER_SECRETS`, the org-wide `PINATA_JWT`. Union injects it into the dashboard pod, and the app record keeps only a reference (`key: "PINATA_JWT"`, `mount_requirement: ENV_VAR`; [Configuration → The public tier](../../../docs/architecture/configuration.md#the-public-tier)). The record holds no part of the key's value. The devbox drops app secrets (the header of `devbox/setup.sh`), so a devbox dashboard has no key: the public routes 503 and the explorer offers no Public source, while Mine works. A shared org key reachable from any task (every task environment declares it) means Pinata's private network would hide nothing between users, so nothing uses it: `PinataClient` works on the public network only, and Mine is the owner's own index (`app.assets._get_index`) and store. On the dashboard Union's login sits in front of the routes; `app/assets.py` keeps its own signed-in check so its per-record ownership rules stay testable on a bare router.

- **Owner stamping.** A public `/assets/tus` upload stamps the signed-in user's subject as `_owner` *after* `build_asset()` validation, and Pinata's upload is created with those keyvalues server-side, so the browser sends bytes only and can't forge it. Workspace/SDK uploads stamp from `STARGAZER_OWNER` instead; [types.md](../../../docs/architecture/types.md) owns that. The launcher injects the variable into per-notebook pods (`env.env_vars["STARGAZER_OWNER"]` next to `FLYTE_PROJECT`), and `config._stargazer_env_vars()` forwards it into task pods at submission so pipeline outputs are owned too. `build_asset()` rejects user-supplied `_*` keys so the namespace stays clean.
- **Metadata edit (`update_metadata`).** A mis-tagged record is fixed in place rather than delete-and-re-uploaded. `PinataClient.update_metadata(cid, keyvalues)` looks up the file's internal UUID by CID, then `PUT /v3/files/public/{id}` with the patch — Pinata **merges** (verified empirically: supplied keys added/overwritten, omitted keys preserved, no key removal), and the bytes/CID are untouched so `*_cid` provenance edges survive. It stamps nothing: the caller's patch carries `_owner`, which the route sets to the signed-in user's subject. `StorageClient.update_metadata(cid, keyvalues)` merges onto the user's own index row only, restamping `_owner` from the env. The MCP `update_file` tool validates via `build_asset` and merges onto the user's own index row, not Pinata. The `POST /assets/update` route additionally **fail-closes on ownership** for public records — the record's current `_owner` must match the signed-in user, read fresh from Pinata not the public TTL cache, so a shared-JWT user still can't rewrite another user's or an unowned record from the page. Editing is the headline reason the bare `cid` is *not* treated as a relationship key in the graph — a content-addressed id never changes under a metadata edit.
- **Public TTL cache.** `_public_cache` (module global, `PUBLIC_CACHE_TTL` = 60s) holds one unfiltered public-network listing; the `public` source filters it in-memory. So anonymous public browsing costs ≤1 Pinata listing call per TTL regardless of traffic, and the dashboard acts as a semi-static mirror. Refresh is single-flight (`_public_cache_lock`, double-checked) so concurrent misses share one listing.
- **Public notebooks** (`app/public_notebooks.py`) reuse this plumbing: `_pinata()` for the upload (`tus_create` plus `tus_patch` per `TUS_CHUNK_BYTES` piece of the file, with the keyvalues stamped `_owner` = the dashboard's owner), `get`, `query` and `delete`, and `_public_records()` for the slugs the owner has published, which decide each workspace tile's Unpublish; public notebooks reach the explorer through the `public` source like any record. After the upload, `get(cid)` must come back as the owner's record for that slug: Pinata dedupes identical bytes per account and keeps the first upload's keyvalues (measured 2026-10-26), so a mismatch means the bytes were already public under another record, and publishing refuses with 409 before deleting anything. The owner's earlier records are found fresh with `query({asset, slug, _owner})`, re-checked in-process, and deleted by CID (one file per CID per account, so the delete can't hit someone else's). Publish and Unpublish drop the TTL cache (`forget_public_records`), and the page reloads after either. A copy reads the bytes from `PINATA_GATEWAY` with aiohttp (`_read_public`).
- **Client swap for tests.** `_pinata_client` / `_public_cache` are module attributes resolved at call time, so route tests monkeypatch a fake Pinata client and reset the cache (`tests/unit/test_assets_routes.py`, `TestClient` without lifespan).
- **Errors** are FastAPI-standard `HTTPException` → `{"detail": ...}` (401 auth, 400 validation or a non-public network, 503 public assets off), via the `_require_user` / `_require_owner` / `_require_public` guards.

### Template (`app/templates/_assets.html`)

The explorer is a partial of three macros, `style()`, `panel()` and `script()`. `dashboard.html` imports it `with context` and calls them in base's `extra_css` block, as the section after the Workspace, and in its `scripts` block after `/static/launch.js`; the home route passes `username` (the visitor's own subject, which the page compares `_owner` against, so an admin visiting someone's dashboard sees Edit only on their own public records), `public_assets` (`public_assets_on()`: a Pinata key is present and the deploy hasn't turned public assets off) `workspace_configured` (whether Copy to workspace is offered) and `mine_on` (`app.assets.is_owner(visitor)`). Mine renders only for the dashboard's owner, since the listing refuses `mine` to anyone else: an admin visiting a dashboard starts on Stargazer alone. The upload panel always renders; a private upload by anyone but the owner is a 403. The home route also passes `explorer_default`, the owner's saved filter (or the built-in) fitted to the visitor (`_fitted`: sources they aren't offered are dropped, so a non-owner never gets `mine`); it's rendered as the pressed source buttons and as `EXPLORER_DEFAULT`, which the page's `state.filter` starts from and Clear returns to. The Settings modal's summary is written from `settings.explorer_default`, unfitted, and only the owner sees it. It reuses base's tokens/buttons, and its selectors and top-level script names don't collide with the dashboard's own. **The reactive `#sky` starfield is untouched** — the asset graph is a separate foreground canvas inside the card.

The graph is rendered by **force-graph** (vasturiano, MIT), vendored as `app/static/force-graph.min.js` (pinned 1.52.0, ~170 KB, d3-force bundled) and `<script src>`-loaded with the browser. This is the one deliberate exception to the app's "ship only hand-written JS" convention (base.html's starfield is still hand-rolled): the project has no bundler, so a single vendored min.js (no build step, served by the existing `/static` mount) carries the canvas, zoom, pan, node drag and the force simulation. To update: re-fetch the pinned version from jsdelivr into the same path. The rest of the page JS is dependency-free vanilla. The Public source button and the Public upload option are gated in the template (`{% if public_assets %}`). A `state` object (`filter`: `sources` and `types` as Sets, `keyvalues`, `text`; view, `records`, `visible`, `selected`, `editing`, `schema`) is the single source of truth. `records` is the `/assets/list` payload for the pressed sources, fetched with `source` params only; `applyFilter()` narrows it to `visible` (`matches`) and redraws the filter bar, graph, list and card, so typing, a chip or "filter by this" costs no request. Toggling a source (`aria-pressed`, several at once) refetches. A type chip's count is the entries matching everything but the types, so pressing it shows that many. The graph and list are two renderings of `visible`, so toggling Graph⇄List re-renders from memory. A card's links resolve among `visible` too. `setFilter(f)` (Clear) refetches only when the sources change. `/assets/list` still takes keyvalue params for other callers; the page doesn't send them. The same CID can be in two sources (a file stored privately and published), so an entry's identity is `source:cid` (`entryKey`): graph node ids, list rows, selection and the edit target all use it, and a `*_cid` link lands on the entry in the linking record's own source first (`linkTarget`). A record's download and edit go to its source's store (`NETWORK`: `mine` → `private`).

- **Graph edges from `companion_of` and `*_cid`.** `relKeys()` selects `companion_of` and every keyvalue ending in `_cid`, with a non-empty value (bare `cid` excluded); `graphElements()` draws an edge from the record to the entry whose `cid` matches the value (`linkTarget`), labeled by `relLabel()`: the key minus `_cid` (`reference_cid` → "reference"), or "companion of". The typed link fields (`companion_of` on the six index and dictionary types; `reference_cid`, `r1_cid`, `mate_cid`, `alignment_cid`, `variants_cid`, `source_cid` on the rest) ride in `keyvalues` from `to_keyvalues()`; custom/bare assets carrying their own `companion_of` or `*_cid` rows link too.
- **Dangling edges** (a `*_cid` value with no matching node in the current set — outside the public listing, or unloaded) are **not drawn**; instead the detail card lists *all* of a node's links, resolving in-view targets to a clickable chip and showing the rest read-only as "not in this view," so provenance is never hidden.
- **Layout** is a live d3-force simulation (`createGraph`, created once as `fg` and fed `graphData` on each render). `graphElements(records)` returns `{nodes, links}`; node objects live in `graphNodes` (keyed by `entryKey`) across renders, so a star that stays keeps its `x`/`y` and only new ones are placed, beside a star they link to or at their type's anchor, and grow in (`born`). Forces: link (distance 14 for `companion_of`, 36 otherwise), charge −45, `anchorForce` (a weak pull to the type's point on a ring, `typeAnchor`) and `collideForce` (pairwise, through velocity, radius + 8). force-graph's `center` force is removed: the anchors' ring centers the sky, and centering would shift every star whenever a filter moved the centroid. A fetch's layout settles after `LAYOUT_TICKS` (400), not a time limit, so a throttled background tab doesn't freeze a half-done layout. A filter change instead pins the stars that stay (`fx`/`fy`, marked `pinned`) and settles the new ones among them with `SETTLE_DECAY`/`SETTLE_TICKS`; `onEngineStop` unpins them and restores the layout cooling, which a drag then settles with. Stars that drop out stay in the data for `EXIT_MS`, marked `died`, pinned, with no charge, collision, anchor or pointer area, shrinking and fading, and `exitTimer` then drops them; one that comes back is revived and grows in again. force-graph stops redrawing once the engine stops; `redrawGraph(ms)` re-sets the paint accessor for one frame and turns `autoPauseRedraw` off for `ms`, so a hover fade (`FADE_MS`, stepped per star by `dimOf`) or the search pulse (`PULSE_MS`, a ring on each shown star after a keystroke) plays out, then the graph is idle again. Nodes are capped at `NODE_CAP` (1,000) with a "showing N of M" hint past the cap.
- **Look.** `paintNode` draws each star on the canvas: a radial glow and a core sized by degree, in `hueOf(type)`; the user's own entries (Mine, or a public record they own) at full alpha and other public ones at 0.6; notebooks as four-point stars; Stargazer entries and the focused star with a ring; labels fade in from zoom 1.1 to 2. `TYPE_HUES` is the dataviz reference categorical order stepped for dark surfaces, validated (adjacent pairs) against the page's `--bg`; `assignTypeHues()` gives the loaded types, sorted, slots in fixed order (gray past eight), and the type chips draw the same hue as a swatch. Links are thin low-alpha lines; particles drift from derived asset to source only on the hovered or selected star's links, so an idle graph with nothing selected costs no frames. The starfield is a static CSS background on `#graph-region`.
- **Interaction.** force-graph gives scroll/pinch zoom, background drag to pan and node drag (which pulls linked stars through the simulation). `onNodeHover` sets `hoverNode`/`hoverSet` (it plus its neighbors), which dims the rest and shows the `graph-tip` tooltip (positioned via `graph2ScreenCoords`); hovering a type chip sets `hoverType`, which dims other types. `onNodeClick` → `selectAsset()` plus an animated `centerAt`/`zoom`; a background click clears; a container `dblclick` calls `zoomToFit`, which also runs once when a fetch's layout settles. Selection is `state.selected`, read by the painter, so a list row and a star stay in sync (`selectAsset()` is shared). Under `prefers-reduced-motion` the layout runs as warmup ticks before the first frame, and there are no particles, growth, exits, fades, pulses or fly-to transitions. Clicking pins the **detail card** (source, full metadata, system `_*` keys dimmed, linked-asset chips, a Download button → `/assets/download/{cid}?network=`, and **Edit metadata** on owned records).
- **Notebook cards** (`renderNotebookDetail`, any `asset=notebook` entry) show the title, description and file name instead of the metadata grid, and no editor. A built-in one gets a `.launch-group` of Edit/Run `form.launch-form`s (`section` is its `category` plus `s`, as `/launch` names it), the same markup a workspace tile has, so `/static/launch.js` drives it: its delegated submit and Stop handlers, and `hydrateLaunches(card)`, which the card calls on every render to flip a running or building notebook to Open/Stop. A workflow (`section=workflows`, its slug) or a public notebook (`section=public`, its CID) adds Copy to workspace (`data-copy-slug`, the same delegated handler), and every notebook a Download source link.
- **Launch code** (`app/static/launch.js`) is shared by the workspace tiles and the explorer's cards: launch, build watch, Open/Stop, re-serve on reopen, copy, `fetchJSON` and `hydrateLaunches(root)`. A build is watched by one `/launch/status` poll per `slug:mode` (`buildWatches`): a card re-rendered while its notebook builds hands that poll its new row and form instead of starting another. It works on any `.launch-group` (a tile's `.tile-actions`, or a card's group), so the dashboard's own script keeps only the workspace actions.
- **Upload** is schema-driven from `/assets/schema`: a typed mode (inputs per field, non-`str` values JSON-encoded to match `from_keyvalues()`) and a visually-distinct custom/bare mode (dashed framing, generic notice, asset-key input). Both share the free-form **+ Add field** k/v rows below (`addExtraRows()`), which reserve `asset`/`cid`/`name`/`_*`: in custom mode they are the whole record, in typed mode they are extra keys beside the declared fields ("Extra fields are stored as text"), and a row naming a declared field is refused in the browser. A Network radio picks Private (the default) or Public, which only shows when `public_assets` is on. The type list leaves out `notebook` (`/assets/schema`), so no upload makes one. Either network's submit sends the file over TUS to `/assets/tus` (`uploadTus()`, the network in `Upload-Metadata`) and takes the CID from the last response's `Stargazer-Cid`. A private one then refetches the list when Mine is on; a public one, when Public is on, **optimistically inserts** a record (the CID, the file's name, the form's keyvalues with `_owner` set to the visitor) into `state.records` so it appears before Pinata's list catches up. The 10 GiB cap is `TUS_MAX_BYTES` for both, checked in the browser and at creation.

## Runtime Init

The same `init()` (`app/init.py`) works locally and in-cluster:

| Context | Signal (checked in this order) | Call |
|---------|--------|------|
| API-key context | `FLYTE_API_KEY` set | `flyte.init_from_api_key(...)`, with `app.config`'s project and domain, and the remote image builder on Union: a key carries no config file to supply them |
| In-cluster app pod | `_U_EP_OVERRIDE` set | `flyte.init_in_cluster(org=FLYTE_ORG, project=…, domain=…)` |
| Local dev / deployer | neither set | `flyte.init_from_config()` |

FastAPI's lifespan calls `init()` once at startup so subsequent SDK calls have a configured client.

## Images (build & publish)

The dashboard and the per-notebook pods share a strict split:

- `app_env.image` is Flyte-built via `with_uv_project` — the dashboard is small Python with no heavy deps, and the Flyte builder is the natural fit.
- Per-notebook envs use the **`notebook-app`** image, defined programmatically as `notebook_app_img_recipe` in `app/per_notebook.py` (proxy, launch script, bioconda CLIs, Claude Code, SDK source at `/stargazer`). Claude Code's context is `app/notebook_agent.md`, copied into `/workspace/` and renamed `AGENTS.md`, which Claude Code (2.1.277 on) reads from the directory it starts in when there's no `CLAUDE.md`; the terminal starts there. The copy goes into a directory and is renamed after, like `proxy.py`, because the builder takes a copy's destination as a directory. Hydration writes the user's stored files over it, and the proxy's startup seed (`_seed_from_disk`) records what's on disk as saved, so the baked copy is never uploaded unless edited, and an edited copy is stored and hydrated over the baked one on every later launch. The dashboard references the exact build via `Image.from_base(config.NOTEBOOK_IMAGE)` so it never tries to (re)build the image itself — a dashboard pod has no Docker daemon or project source layout. The one image it does build is a notebook's declared `main_env` image, layered on this one, which its `serve` builds remotely (Notebook-Declared Environments above). (The project `Dockerfile` — `stargazer` — mirrors this recipe for local `docker run`: same layers and launch script, multi-arch downloads, no Flyte runtime. It shares no code with the recipe, so pins (Claude Code, marimo) and the bioconda set can lag. `tests/unit/test_dockerfile.py` checks that it ships the files the proxy reads beside itself, installs the pip packages the hosted recipe pins, and bakes the notebook agent context as `/workspace/AGENTS.md`. It is *not* the hosted build.)

A deploy run builds the recipe with `flyte.build` once (`deploy.build_notebook_image`) and bakes the returned content-hashed URI into each dashboard it deploys as `STARGAZER_NOTEBOOK_IMAGE`. The dashboard image is built by the serve itself, also content-hashed. An unchanged recipe is a registry hit, so a release builds each image once. Every per-notebook pod therefore runs exactly the build that shipped with its dashboard: no mutable tag, no `docker buildx` retag, and no chance of a node serving a stale cached `:latest`. A per-notebook pod picks up new proxy/launch code on its next re-serve after a redeploy (the dashboard's Open re-serves).

**On Union images build on Union's remote builder** (`image.builder: remote` in `.flyte/union.yaml`) and push to Union's registry, so the deployer needs no Docker daemon or registry login. A pull failure with `no processor for media-type application/vnd.oci.image.layer.nydus.blob.v1` means the remote builder produced a Nydus-only image the nodes can't pull.

## Deploy targets (devbox vs union)

`STARGAZER_TARGET` (`devbox` default, or `union`) is the one switch between the local devbox and the hosted Union tenant. `stargazer.config` validates it (a typo is an import error, not a silent devbox), and forwards it, plus any explicit `STARGAZER_REGISTRY`, into every pod via `STARGAZER_ENV_VARS`, so in-pod builds resolve images the same way the deployer does.

| Setting | devbox | union |
|---|---|---|
| Deployer's Flyte config (`app.config.FLYTE_CONFIG`) | `.flyte/config.yaml` | `.flyte/union.yaml` (remote builder) |
| `STARGAZER_REGISTRY` default | `localhost:30000` | unset: the remote builder pushes to Union's registry |
| Login | none: a stand-in user (`SG_STAND_IN_SUBJECT`) for requests with no subject, never honored on Union | Union's gate |
| Dashboard deploy | `devbox/dashboard.py`: one dashboard for the stand-in user (each setting's reason is in its docstring) | `deploy_dashboard`, called by infra's onboarding: one per user in their project |
| Object store | rustfs inside the devbox, reached through `FLYTE_AWS_*` | the tenant bucket, through the pod's role |
| Asset index | Postgres in the `stargazer` namespace (`devbox/postgres.yaml`, applied by `devbox/setup.sh`), reached directly by the dashboard and every pod | each user's table on Aurora DSQL, reached directly by their dashboard and every pod in their project |

`FLYTE_DOMAIN` (default `development`) is independent of the target: it's the domain dashboards deploy into, and where dashboards serve and look up per-notebook apps, so a prod deploy sets `FLYTE_DOMAIN=production`. Both `.flyte/` files are gitignored; create `union.yaml` with `flyte create config --endpoint dns:///<tenant> --image-builder remote -o .flyte/union.yaml`.

## Deploy Settings

No secret is required to deploy. The deployer's shell supplies these (infra keeps the tenant's values in its `tenant.env`):

| Env var | Purpose | If absent |
|---|---|---|
| `STARGAZER_TARGET=union` | picks `.flyte/union.yaml` | the devbox is targeted |
| `STARGAZER_WORKSPACE_ROOT` | where users' notebooks and assets live; baked into every dashboard and pod | the dashboard has no store: store-backed routes answer 503 |
| `STARGAZER_ADMIN_SUBJECTS` | comma-separated Union subjects of the org admins who may open every user's dashboard and notebooks; baked into every dashboard, which passes it to its pods | only each dashboard's owner gets in |
| `STARGAZER_PUBLIC_ASSETS=off` | turns public assets off in every dashboard the deploy touches (`app.config.PUBLIC_ASSETS`): the explorer offers no Public source, the public upload option is gone, and the public routes answer 503, as with no Pinata key. Tasks and notebooks keep the public tier | public assets are on wherever the Pinata key is |
| `STARGAZER_DSQL_CLUSTER_ARN` | the org's Aurora DSQL cluster. Every deploy gives the dashboard the user's `dsql://` index URL (`deploy.dsql_index_url`), built from names alone, so a deploy needs no AWS access; the dashboard passes it to its notebook pods. Infra's onboarding makes the table, login and IAM role it names | a deploy is refused, unless it brings its own index (the devbox's Postgres) |
| `PINATA_GATEWAY` | the account's dedicated gateway (`https://<name>.mypinata.cloud`) for public downloads; rides into every dashboard, notebook pod and run | the same dedicated gateway: it's the SDK's default (`config.py`) |

Per dashboard, `deploy_dashboard` bakes in the per-user variables (Onboarding above), the deployer's org as `FLYTE_ORG`, and the deployer's commit as `STARGAZER_VERSION` (`git describe --always --dirty`, `unknown` outside a checkout), which the dashboard shows in its footer. The same commit is the deploy's version (`with_servecontext(version=…)`, which reaches the pod as `fserve --version`), so the console shows what each dashboard runs. A version is a label, not a key: redeploying under one the app already has, with a changed spec, still makes a new revision. Deploys stay on `serve` rather than `flyte.deploy`, which takes its project from init (each dashboard is in its user's project) and doesn't wait for the app to come up.

Redeploying existing dashboards only lists projects, builds images and deploys apps, so it can run under an API key: export `FLYTE_API_KEY` (from `flyte create api-key`) along with the settings above, and `init` skips the config file. Image builds then run in `FLYTE_PROJECT`, `flytesnacks` unless it's set.
