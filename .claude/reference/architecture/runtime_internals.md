# Notebook Runtime — Internals (agent reference)

Implementation-level detail for the notebook pod (`runtime/`): the companion to the human-facing [docs/architecture/runtime.md](../../../docs/architecture/runtime.md). It carries the protocols that span the launch script, the proxy and the image. When you change hydrate, save, the signal path or the proxy's data path, read this first and update it after.

## The Image

`runtime/Dockerfile` is the one recipe, for every place a notebook runs. On a cluster the image runs under Flyte's `fserve`, set as the container's command, which downloads the launching app's code bundle and writes its parameters file into the working directory, then runs the launch command with `Popen(..., shell=True)`. So the working directory is `/home/flyte`: in `/workspace` the proxy would save the bundle and the parameters file as the user's files. The bundle can hold an `app/` package (the dashboard's), which is why the proxy is the top-level module `sg_proxy`, on `PYTHONPATH=/usr/local/lib`.

Claude Code's context is `runtime/notebook_agent.md`, baked as `/workspace/AGENTS.md`, which Claude Code reads from the directory it starts in when there's no `CLAUDE.md`. Hydration writes the user's stored files over it, and the proxy's startup seed (`_seed_from_disk`) records what's on disk as saved, so the baked copy is never uploaded unless edited, and an edited copy is stored and hydrated over the baked one on every later launch. Run locally, `runtime/start-local.sh` writes a local-persistence Flyte config to `~/.flyte` (there's none in the image, so a hosted pod's in-cluster init never meets it) and copies `/opt/workspace`, the notebooks and `AGENTS.md`, into `/workspace` with `cp -n`.

The release workflow (`.github/workflows/release.yml`) builds it for amd64 and arm64 on a calendar tag and pushes `ghcr.io/stargazerbio/stargazer:<tag>` and `:latest`. Union's nodes pull it from GHCR, which is public. A notebook's declared image (`main_env`) is built on top of it, by Union's remote builder in the owner's project.

## Pod Hydrate & Save

The pod is a working copy; the store is the durable one. The pod manager never calls a pod (a pod behind the login is unreachable server-to-server), so the pod does both ends itself.

1. **Hydrate.** `launch-notebook.sh` runs `sg_proxy.hydrate()` before starting marimo: every object under the owner's `workspace/` prefix lands at its path in `/workspace` (`fs.find`, then each object's path relative to the prefix with the URI scheme stripped, since S3 lists `bucket/key`). A brand-new user, or a store failure, starts with an empty dir (logged, never fatal).
2. **Starting page.** The proxy answers immediately; until marimo is up, a browser request gets a self-refreshing "Starting your notebook…" page. `/__sg__/ready` reports 200/503 for scripts.
3. **Save on an interval.** A background loop walks `/workspace` (`_workspace_files`: no dotfiles or dot-dirs, no `__pycache__/` or `__marimo__/`, symlinks not followed) and uploads each file whose size or mtime differs from what it last stored, each to its own key. An unchanged file is never read. The stamps of just-hydrated files are seeded at startup, so the first pass doesn't re-upload them. A failed upload is logged and retried next pass. One PUT per object, so an interrupted upload can't leave a half-written file. The interval is `SG_SAVE_INTERVAL_SECONDS` on the pod, 30 when unset. The pod manager sets it at launch (the dashboard from the user's save-interval setting), so a running pod keeps the interval it started with. 0 starts no loop.
4. **Deletes follow.** A pass deletes from the store each file it hydrated or saved (a key of `_synced`) that's gone from `/workspace`. Nothing else: after a failed hydrate the workspace is empty, and mirroring it would wipe the store. The other way round, a changed file it hydrated or saved that's gone from the store (`flyte.storage.exists`, checked only for a changed file) was deleted elsewhere, by the dashboard's delete while the pod was still up, and isn't uploaded; its stamp is recorded, so it's checked again only when it changes again. Without that, the pass after the delete puts it back whenever it changed since the last pass, and a pod deleted while starting always has: marimo rewrites the notebook as it opens. A pod whose notebook isn't there after the hydrate (deleted before the pod started, or a failed hydrate) gets a blank one from marimo; the launch script names it in `SG_UNSAVED_NOTEBOOK`, and no pass uploads it, or it would undo the delete, or after a failed hydrate overwrite the stored notebook. It's skipped in the upload loop only, so the delete loop can't remove the stored one either.
5. **Big files stay out.** A file over `MAX_SAVED_BYTES` (100 MB) is skipped without being read. `GET /__sg__/save-status` lists such files, read from disk on each request so it works with the loop off, and `runtime/save_banner.html`, spliced into every marimo page beside the terminal overlay, polls it every 10 s and shows each one with the cell that stores it as an asset (`default_client.upload(build_asset(...), Path(...))`), which writes from the pod straight to the store and the index.
6. **Save at shutdown.** The FastAPI `lifespan` shutdown hook cancels the loop and runs a final pass when Knative scales the pod to zero.

The signal path is load-bearing for step 6. Flyte's `fserve` wrapper is PID 1 and, on the Knative SIGTERM, forwards the signal to its **one direct child only** (`Popen(cmd, shell=True)` + `send_signal`). So uvicorn must be that direct child: the launch command starts with `exec` (so the `sh -c` wrapper replaces itself with the launch script rather than lingering; Debian's `/bin/sh` does not reliably exec-collapse a bare `sh -c "script"`), and the launch script then `exec`s uvicorn into that slot. An intermediate shell anywhere in the chain swallows SIGTERM and the final save is silently skipped.

Receiving SIGTERM is necessary but not sufficient: uvicorn drains open connections and in-flight background tasks **before** running the `lifespan` shutdown. The proxy holds a long-lived task to the local marimo backend that never drains on its own, so with uvicorn's default `timeout_graceful_shutdown=None` the drain blocks forever and the final save never fires (verified empirically). The launch script therefore passes `--timeout-graceful-shutdown 15`, which bounds the drain, cancels the lingering task, and then still runs `lifespan.shutdown`. 15s sits well under the pod's 300s termination grace period.

## The Proxy Data Path

- **Proxy:** the standalone `runtime/proxy.py` (which imports no Stargazer code) keeps one module-local shared client with keep-alive to loopback marimo (`_upstream_client`, closed in the proxy lifespan after the shutdown save). Only `text/html` responses are buffered — for the terminal overlay and save banner splice; everything else (static bundles, API JSON, downloads) **streams** through chunk-by-chunk (`StreamingResponse` over `aiter_raw`, `BackgroundTask(resp.aclose)`) with its original headers, so large bodies never sit in proxy memory. The raw query string passes through untouched (duplicate params intact), hop-by-hop, cookie and `X-User-*` headers are stripped, and the request body is streamed only when one exists (no gratuitous chunked framing on GETs).
- **Compression:** the proxy relays marimo's own encoding untouched.
